# 多轮对话改进方案（讨论稿，尚未实现）

> 状态：2026-09-17 讨论定稿，**还没有改任何代码**。第一阶段范围已确认：C + D + A（极简版）；
> B（滚动摘要）延后。
>
> 已对齐的前提：**质量优先、成本其次**；分两阶段推进。

---

## Context

现状（已逐行核实代码）：

- 会话存服务端（`.web_conversations.json`）、按用户隔离。
- 每轮存：原问题、答案（≤8000 字）、检索方式、命中的切片引用（丢正文）。
- **改写后的问题不落盘** —— 只在 job 运行时的内存里，审计/评估都看不到。
- `answer_question` 里：
  - 改写用 `_history_text`（每轮答案 ≤500 字）→ 供检索。
  - 生成用 `_history_messages`（每轮答案 ≤2000 字）→ 供答案。
  - 窗口 `MAX_HISTORY_TURNS = 8`。
- 压缩 = **纯硬截断**（8 轮 + 字符上限），没有语义摘要。

两条已确认的设计结论：

- **A 不做大**：追问里的「它」大多指上轮**回答的结论**，而回答文本已经在改写 prompt 里。
  极简版只喂上一轮 top-3 命中切片，解决「指代只存在于原文、不在上轮问答」那类失败
  （真实存在，但较少见）。注意 `resolve_chunks` 按**当前索引**取正文，重建后 chunk_id
  会漂移——作为 prompt 提示它会优雅降级（最坏只是无关线索），不是事实源。
- **B 延后**：需要**会话级锁**（`answer_limiter` 是全局信号量，`answer_jobs._run` 在任务
  锁外读历史/append，同一会话两个 job 会双算折叠）；且摘要是「二手上下文」，质量未必
  升反降。这两点代价现在就能预见。

## 第一阶段

### C. 改写后的问题落盘（收益最确定，零 LLM 成本）

解锁两件事：审计能复盘「这一轮检索实际用了什么」；评估工具能拿**真实追问**当测试题
（现在 `eval import-conversations` 只取首轮，因为追问没有独立问题可用）。

- `app/conversations.py` `append_turn`（:98）：加可选参 `retrieval_question: str = ""`，写入 turn 字典。
- `app/service.py` `answer_question`：`AnswerResult`（:585）加 `retrieval_question` 字段；
  返回 dict 里带上它（condense 跳过时它就是原问题）。`AnswerResult` 是 TypedDict，加字段
  不破坏现有读取方（`_handle_ask` 只取几个键）。
- `app/answer_jobs.py` `_run`（:175 附近）：`append_turn(..., retrieval_question=result["retrieval_question"])`。
- 旧数据兼容：读旧 JSON 用 `.get("retrieval_question", "")` 兜底，不迁移。

### D. 提示词澄清（零成本，别抱高期望）

`chains/prompts.py` `ANSWER_PROMPT` 的 system 消息补一句：对话历史用于**理解当前问题的
指代**，不要复述或反驳其中的旧结论，回答以**当前检索到的上下文**为准。措辞要留口子——
用户有时确实想让模型延续之前的结论，「以当前上下文为准」是核心约束，别把「延续」也禁掉。

### A. 锚定改写（极简版）

解决「它的预训练目标……」「这些方法……」这类指代只存在于原文的追问。

- `app/conversations.py` `history_for`（:167-180）：返回的每条 turn 加上 `hits`
  （`.get("hits") or []`）。签名注释从 `list[dict[str,str]]` 改宽；消费方
  `_history_messages` / `_history_text` 只读 question/answer，天然兼容。
- `app/service.py` `answer_question` 的改写块（:1055 附近）：收集 `history[-1]`（上一轮）
  的 `hits[].chunk_id` 前 3 个，`resolve_chunks`（:829，评估工具里已有的现成函数）取回
  正文，拼成 ≤ ~600 字的一段，传给 `condense_question(context_snippets=...)`；取不到就传
  None（优雅降级）。
- `chains/answer_chain.py` `condense_question`（:48）：加可选参 `context_snippets: list[str] | None = None`，非空时注入 prompt。
- `chains/prompts.py` `CONDENSE_PROMPT`：加一个 `{context}` 块（可选），措辞：
  「以下是上一轮检索命中的原文片段，用于理解新问题里的指代（如『它』『这』）。
  不要照搬片段，改写仍以『新问题 + 历史』为准。」
- 触发条件：仅当 `history` 非空（与现状一致）且上一轮确实有命中。

## 第二阶段（延后，不在本次实现）

**B. 滚动摘要（长对话记忆）** —— 前置条件写清楚，免得以后忘：

- 必须先给**同一会话的并发 job** 加会话级锁（`answer_jobs` 里当前只在任务锁内做快照、
  锁外读写历史与 append），否则折叠计数与摘要会被双算。
- `conversations.py` 加 `summary` 字段与 `fold_into_summary`；`history_for` 改成返回
  「summary + 近期轮」；折叠触发阈值、摘要长度封顶、失败回退都要定。
- 与「8 轮窗口 + 500/2000 字符」共存：折叠后的轮次从窗口里移出，只留摘要。
- 摘要是**二手上下文**：做完第一阶段、看过真实多轮效果后再决定要不要。

## 验证

1. `pytest -q` 全绿（319 不破；新增/更新测试见下）。
2. **单元**：
   - C：`append_turn` 带 `retrieval_question` 后 turn 里有该字段；不带时默认空；旧 JSON 读取不炸。
   - D：无行为断言（纯 prompt 文案），靠回归。
   - A：monkeypatch `chains.answer_chain.condense_question` 捕获参数，断言带 history 时
     传入了 `context_snippets`（且只含上一轮、最多 3 片、取不到时为 None）；
     `history_for` 返回的 turn 带 hits。
3. **端到端（浏览器 + 真实多轮）**：同一会话连问两轮，第二轮是「它的/它们的……」类追问，
   观察（a）过程栏「问题改写」显示的独立问题是否包含真实指代（b）对话存储里第二轮存了
   `retrieval_question`（c）答案能接上第一轮的话题。
4. 确认 `/api/conversations` 详情返回的轮次里有新字段，且旧会话（无该字段）正常显示。

## 不做

- **不做 B**（延后，见第二阶段）。
- **不做 E**（成本优化：跳过改写启发式、便宜改写模型）—— 用户已表态成本其次，且跳过
  改写的启发式容易误判独立而引入 bug。
- 不改窗口大小 / 截断常量（`MAX_HISTORY_TURNS` / 500 / 2000）—— 那是另一个决策，本次不碰。
